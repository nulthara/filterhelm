## Problem

`frontend/` has no test tooling. There is no test runner and no `npm test` script, so the
only check on page logic is clicking through the UI. The riskiest untested logic is the
bulk-action loop, and four pages each carry their own copy of it: `AdlistsPage.tsx`,
`DomainsPage.tsx`, `DNSHostsTab.tsx`, and `DNSCnamesTab.tsx`. Each copy awaits one instance
at a time, which protects invariant #1 and avoids the concurrent-login 401. Each one catches
a failure per instance so the remaining instances still run, and each builds the same
summary message. `DNSHostsTab` also splits a selection into 200-record chunks and stops an
instance's remaining chunks after a throw. Plan 0010 left that chunking path unverified,
both live and in tests. `docs/potential-features.md` §5 tracks this gap. The four copies
can drift apart without anything noticing.

## Scope

In:
- Add Vitest as a frontend dev dependency and an `npm test` script.
- Move the bulk loop and summary into one module, `frontend/src/bulk.ts`.
- Make the four pages call it, with no change in behaviour or message text.
- Unit-test `bulk.ts` in Node with no DOM.
- Add `npm test` to every place that lists the frontend checks.
- Rebuild and commit `app/static/ui/`.

Out:
- Component or DOM tests. That means no jsdom and no `@testing-library/*`. The
  selection-clearing rules stay untested.
- Any change to the confirm modals, the target-building code, or the single-record
  handlers.
- Chunking for adlists, domains, or CNAMEs. Only DNS hosts chunks today, and the refactor
  keeps it that way.
- A CI test step. `.gitea/workflows/deploy.yml` runs no tests today, pytest included.
- The `source-map-js` high-severity `npm audit` finding. It is already on `main` with
  or without Vitest.
- Backend changes.

## Approach

`bulk.ts` exports two pure functions. Neither imports React, antd, or anything at runtime
from `api.ts`.

- `runBulkSequentially` takes the targets, a `send` callback, and an optional chunk size.
  It runs the loop each page runs today, and the pages pass their `api.bulk*` call as
  `send`. Tests pass a fake `send`, so no network or DOM is needed.
- `summarizeBulk` builds the message text and says whether to show it as a warning.

Each page keeps its own `message.warning` / `message.success` call, `setSelectedKeys([])`,
`load()`, and `setWorking`. Those are React and antd effects, and they stay in the page.

Vitest 5.0.3 is the current release. It declares `vite: ^6.4.0 || ^7.0.0 || ^8.0.0` as a
peer, and the repo has Vite 7.3.6 installed. It also supports Node `>=26`, and the local
Node is 26.10.0. A trial install in a scratch copy of `frontend/` on 2026-10-09 gave these
results:
- npm added 16 entries to `package-lock.json`, going from 293 to 309 `node_modules/` keys.
- The set of URL hosts in the lockfile did not change, so
  `test_tracked_files_use_only_approved_addresses_and_hosts` stays green.
- `esbuild` stays at 0.28.2.
- `npm audit` reports the same single high finding (`source-map-js`) as `main`.
- A sample `src/*.test.ts` ran under `npx vitest run` with no config file.

Vitest's defaults are enough, so `vite.config.ts` does not change. The default include
pattern picks up `src/**/*.test.ts`, and the default environment is `node`.

Rejected alternatives:
- **Extract only the DNS hosts chunking.** Three copies would stay untested and keep
  drifting.
- **Add component tests with jsdom and Testing Library.** That brings more dependencies
  for coverage of selection clearing, which is simple state. It can come later in its own
  plan.
- **Make every page chunk at 200.** That changes behaviour on three pages. This plan is a
  pure refactor plus tests.

## Steps

1. **Install Vitest.** Run `cd frontend && npm install --save-dev vitest@^5.0.3`.
   `frontend/.npmrc` already enforces `min-release-age=1`. Add
   `"test": "vitest run"` to `scripts`, after `lint`. Then run `npm audit`. Expect exactly
   one high finding, `source-map-js`. Any other finding is a stop-and-report. Do not run
   `npm audit fix`. If npm warns that the esbuild install script was blocked, that is
   expected, because esbuild is unchanged at 0.28.2.

2. **`frontend/src/bulk.ts`.** Write it with these exports:

   ```ts
   import type { BulkResult } from './api'

   export const BULK_CHUNK_SIZE = 200

   export interface BulkTarget<T> {
     instance: string
     items: T[]
   }

   export type InstanceBulkResult = BulkResult & { instance: string }

   export interface BulkRun {
     results: InstanceBulkResult[]
     instanceFailures: string[]
   }

   export async function runBulkSequentially<T>(
     targets: BulkTarget<T>[],
     send: (instance: string, items: T[]) => Promise<{ results: BulkResult[] }>,
     chunkSize?: number,
   ): Promise<BulkRun>

   export function summarizeBulk(
     selectedCount: number,
     run: BulkRun,
     unchangedLabel = 'already in that state',
   ): { text: string; failed: boolean }
   ```

   **`runBulkSequentially`** does the following:
   - It loops over `targets` with `for … of` and awaits each instance before starting the
     next. Keep the comment "Invariant #1: await one instance at a time; concurrent
     logins can race into a 401." above the loop.
   - With `chunkSize` undefined, it makes one `send(target.instance, target.items)` call
     per target. This matches Adlists, Domains, and CNAMEs today.
   - With `chunkSize` set, it calls `send` once per slice
     `items.slice(offset, offset + chunkSize)`, for `offset` from 0 while
     `offset < items.length`. This matches `DNSHostsTab` today.
   - After each `send` resolves, it appends that response's results at once, each spread
     with `instance: target.instance`.
   - One `try/catch` wraps all of an instance's calls. A throw stops that instance's
     remaining chunks and keeps any results already appended. It pushes
     `` `${target.instance}: ${error instanceof Error ? error.message : 'Unable to apply bulk action'}` ``
     to `instanceFailures`, then moves on to the next target. Keep `DNSHostsTab`'s comment
     "Stop this instance's chunks after a throw; a rollback failure forbids more writes."
     on the `catch`.

   **`summarizeBulk`** returns the text the pages build today:
   - `changed` is the count of results with `changed`. `unchanged` is the count with
     `success && !changed`.
   - `failures` lists, in order, `` `${r.instance} / ${r.id}: ${r.error}` `` for each
     result with `!success`, followed by `instanceFailures`.
   - `summary` is
     `` `${selectedCount} selected, ${changed} changed${unchanged ? `, ${unchanged} ${unchangedLabel}` : ''}` ``.
   - With failures, it returns `{ text: `${summary}; failed: ${failures.join('; ')}`, failed: true }`.
     Otherwise it returns `{ text: summary, failed: false }`.

   `bulk.ts` imports only the `BulkResult` type from `./api`, so tests never load
   `api.ts` at runtime.

3. **Pages.** In each page's `applyBulk`, replace the block from `const results` through
   the `message.warning` / `message.success` lines with the code below. Keep everything
   before it (targets, confirm, `setWorking(true)`) and after it (`setSelectedKeys([])`,
   `await load()`, `finally`) unchanged.

   ```ts
   const run = await runBulkSequentially(
     targets.map((target) => ({ instance: target.instance, items: target.<field> })),
     (instance, items) => api.<bulkCall>(instance, …, items),
     <chunkSize or omitted>,
   )
   const outcome = summarizeBulk(selectedKeys.length, run<, label>)
   if (outcome.failed) message.warning(outcome.text, 10)
   else message.success(outcome.text)
   ```

   The per-page values are:

   | Page | `<field>` | `send` body | chunk | label |
   |---|---|---|---|---|
   | `AdlistsPage.tsx` | `addresses` | `api.bulkAdlists(instance, action, items)` | omitted | default |
   | `DomainsPage.tsx` | `domains` | `api.bulkDomains(instance, action, items)` | omitted | default |
   | `DNSHostsTab.tsx` | `records` | `api.bulkDNSRecords(instance, items)` | `BULK_CHUNK_SIZE` | default |
   | `DNSCnamesTab.tsx` | `records` | `api.bulkDNSCnames(instance, items)` | omitted | `'already removed'` |

   Import `runBulkSequentially`, `summarizeBulk`, and, in `DNSHostsTab` only,
   `BULK_CHUNK_SIZE` from `'../bulk'`. Remove `type BulkResult` from each page's `../api`
   import, because nothing else in these pages uses it. Leaving it in fails
   `@typescript-eslint/no-unused-vars`. Grep each page for `BulkResult` before removing
   it. If another use exists, keep the import and note it in the report.

4. **`frontend/src/bulk.test.ts`.** Add the tests listed under Tests. Use `vi.fn` for
   `send` and import from `'vitest'` explicitly. Do not rely on Vitest globals.

5. **Build.** Run `cd frontend && npm run build && npm run lint && npm test`. `tsc -b`
   type-checks `bulk.test.ts` too, because `tsconfig.app.json` includes `src`. Vite does
   not bundle the test file, since no entry imports it. Leave the regenerated
   `app/static/ui/` in the working tree for Claude to commit.

6. **Docs and commands.** Add `npm test` next to every existing listing of the frontend
   checks:
   - `ARCHITECT.md` "Definition of done": `cd frontend && npm run build && npm run lint && npm test`.
   - `AGENTS.md` Frontend rules, last bullet: the same command.
   - `CLAUDE.md` Commands: the same command, keeping the trailing comment.
   - `README.md`: add `npm test` as a third line in the `cd frontend` block.
   - `.claude/commands/verify.md`: add `Bash(cd frontend && npm test:*)` to `allowed-tools`
     and `&& npm test` to step 4's command.
   - `.claude/commands/handoff.md`: change "`npm run build` + `npm run lint`" to
     "`npm run build` + `npm run lint` + `npm test`".
   - `.claude/settings.json`: add `"Bash(cd frontend && npm test:*)"` after the lint entry.

7. **`docs/potential-features.md`.** Remove the "A frontend test runner." bullet from §5.
   Add a Shipped bullet above the plan 0028 bullet saying Vitest runs frontend unit tests
   via `npm test`, and that the four bulk pages share a tested runner in `src/bulk.ts` —
   plan 0029. Leave "Suggested next pick" as it is.

## Tests

`frontend/src/bulk.test.ts`. Each test builds `targets` by hand and a `send` from `vi.fn`.
Fake results follow `{ id, success, changed, error }`.

`runBulkSequentially`:
- `waits for each instance before starting the next`. Two targets, `a` and `b`. `send`
  returns a promise the test resolves by hand. Assert that `send` has one call (`a`) before
  `a`'s promise resolves, and two calls after. Then resolve `b` and await the run.
- `sends every item in one call without a chunk size`. One target with 450 items. Assert
  one call carrying all 450.
- `splits items into chunks in order`. One target with 450 items and `chunkSize` 200.
  Assert three calls with 200, 200, and 50 items, and that the first item of each call is
  items 0, 200, and 400.
- `stops an instance's chunks after a throw and continues with the next instance`. Targets
  `a` with 450 items and `b` with 1 item, `chunkSize` 200. `send` resolves `a`'s first
  chunk with one success result, rejects `a`'s second with `new Error('rollback failed')`,
  and resolves `b`. Assert exactly three calls in order: `a` chunk 1, `a` chunk 2, then
  `b`. `a`'s third chunk is never sent. Assert `results` holds `a`'s first result and `b`'s result, each with
  its `instance`. Assert `instanceFailures` is `['a: rollback failed']`.
- `reports a non-Error rejection with the fallback message`. `send` rejects with the
  string `'nope'`. Assert `instanceFailures` is `['a: Unable to apply bulk action']`.

`summarizeBulk`:
- `counts changed and unchanged results`. Results with one changed and two unchanged
  successes, `selectedCount` 3. Assert
  `{ text: '3 selected, 1 changed, 2 already in that state', failed: false }`.
- `omits the unchanged clause when there is none`. One changed. Assert
  `'1 selected, 1 changed'`.
- `uses a custom unchanged label`. One unchanged, label `'already removed'`. Assert
  `'1 selected, 0 changed, 1 already removed'`.
- `lists result failures before instance failures`. A failed result
  `{ instance: 'a', id: 'x', error: 'gone' }` and `instanceFailures` `['b: down']`, with
  `selectedCount` 2. Assert
  `{ text: '2 selected, 0 changed; failed: a / x: gone; b: down', failed: true }`.

Expect `npm test` to report 9 passed. `./.venv/bin/pytest` stays at 643 passed. Run it
after `app/static/ui/` is rebuilt and staged, because the hygiene tests read every tracked
file and the old hashed bundles are deleted on disk until the rebuild is staged.
